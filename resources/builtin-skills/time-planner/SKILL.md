# 赛程时间规划与进度跟踪

比赛最大的隐性失败原因不是题目太难，而是**时间失控**：第三天才定题、最后一晚才写论文、摘要没时间打磨。本技能把赛程当成一个有截止时间的项目来管理。

## 第一步：定参赛参数

用 AskUserQuestion 确认（一次问完，最多 4 问）：

1. 赛事与时长：CUMCM 72h（周四 18:00 → 周日 20:00 提交）/ MCM 96h（周四 18:00 → 周一 上午）——以当届通知为准。
2. 团队分工：三人的主责（建模 / 编程 / 写作），是否有兼任。
3. 选题偏好：A/B/C/D（美赛 A-F）是否有倾向，还是开赛后由 problem-parser 分析再定。
4. 已知约束：课程/睡眠/其他硬性时间占用。

## 第二步：生成里程碑计划（落盘 `plan/timeline.md`）

基准模板（按 72h 国赛，96h 美赛各段 ×1.3）：

| 阶段 | 时间窗 | 硬性出口（不满足不许进下一阶段） |
|---|---|---|
| 0 开题 | 0-2h | 全队读完三道题；problem-parser 产出各题要素清单 |
| 1 选题 | 2-4h | 确定题目与每问思路方向；定版不反悔（除非致命障碍） |
| 2 数据/文献 | 4-8h | data-search 与 literature-search 完成；数据清洗入 `data/` |
| 3 问题一建模求解 | 8-18h | 问题一结果可复现（.py 跑通、图表产出） |
| 4 问题二三建模求解 | 18-40h | 各问结果可复现；robustness-checker 检验通过 |
| 5 论文初稿 | 28-56h（与求解并行） | 每完成一问即写该问章节，禁止"全算完再写" |
| 6 整合与检验 | 56-66h | 全文编译通过；图表编号统一；摘要初稿 |
| 7 摘要打磨 + 合规 | 66-70h | abstract-writer 出终稿；competition-rules 全绿 |
| 8 提交缓冲 | 70-72h | **预留 2 小时只做提交**：转换 PDF、打包、上传重试 |

排期原则：

- **写作与求解并行**是铁律——论文写作总工作量 ≥ 求解，绝不能排到最后 12 小时。
- 每个阶段的"硬性出口"比时间更重要：出口不满足就压缩下一阶段并显式告知用户风险。
- 内置 20% 缓冲不单列，体现在各段收口时间的富余里。

## 第三步：跟踪与预警

每次会话开始（或用户说"复盘/同步进度"）时：

1. 读 `plan/timeline.md` 与当前时间，算各里程碑状态（按时 / 风险 / 已延期）。
2. 对照任务面板与 `solve/` 产物修改时间，核实实际进度（不轻信口头汇报）。
3. 延期处理：给出**具体的压缩建议**（"问题二启发式迭代次数减半先出结果"），而不是"要抓紧"。
4. 进度重大变化（跳题、推倒重来）时重排时间表并标注 diff。

## 产出

- `plan/timeline.md`：里程碑表（阶段/起止/出口/状态），随进度更新。
- 每次复盘在对话里给一份"当前 vs 计划"对照 + 未来 12 小时的行动清单（按人分工）。
